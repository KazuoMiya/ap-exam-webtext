Q: 関係データベースの表で、索引を作成しても、検索の高速化の効果が最も小さい列はどれか。
ア: 値が行ごとに異なる、会員番号の列
イ: 検索の条件に頻繁に指定される、受注日の列
ウ: 結合の条件に使われる、外部キーの列
エ: 値の種類が二つしかない、有効か無効かを表す列
正解: エ
解説: 値の種類が少ない列では、条件を指定しても行を少数に絞り込めないので、索引を使っても全件を読むのと変わりません。索引は、**絞り込みの効果が大きい列**に作成します。索引を増やすと、更新のたびに索引も更新するので、更新は遅くなります。

Q: 分散データベースに関するCAP定理の説明として、適切なものはどれか。
ア: 原子性、一貫性、独立性、耐久性の四つを満たせば、分散処理ができる。
イ: 一貫性、可用性、分断耐性の三つを、同時にすべて満たすことはできない。
ウ: コミットの処理を、準備と確定の二つの段階に分けて行う。
エ: 複製の数を増やすほど、一貫性と可用性の両方が高まる。
正解: イ
解説: **CAP定理**は、一貫性（Consistency）、可用性（Availability）、分断耐性（Partition tolerance）のうち、同時に満たせるのは二つまでであるという定理です。ネットワークの分断は避けられないので、実際には、分断の間に一貫性と可用性のどちらを優先するかを選びます。

Q: 「顧客」表と「注文」表がある。一度も注文していない顧客を求めるSQL文の WHERE 句として、適切なものはどれか。SQL文は「SELECT 顧客番号 FROM 顧客 WHERE …」の形式である。
ア: EXISTS (SELECT * FROM 注文 WHERE 注文.顧客番号 = 顧客.顧客番号)
イ: 顧客番号 IN (SELECT 顧客番号 FROM 注文)
ウ: NOT EXISTS (SELECT * FROM 注文 WHERE 注文.顧客番号 = 顧客.顧客番号)
エ: 顧客番号 = ALL (SELECT 顧客番号 FROM 注文)
正解: ウ
解説: 相関副問合せは、「顧客」表の1行ごとに評価されます。その顧客の注文が1件もないときに、**NOT EXISTS** が真になります。EXISTS と IN は、注文したことのある顧客を求めます。

Q: 親の表の行を削除したときに、その行を参照している子の表の行も、同時に削除されるようにする参照動作の指定はどれか。
ア: ON DELETE CASCADE
イ: ON DELETE NO ACTION
ウ: ON DELETE SET DEFAULT
エ: ON DELETE SET NULL
正解: ア
解説: **CASCADE** は、親の行の削除や更新を、子の行にも連鎖させます。NO ACTION は、参照している子の行があれば削除をエラーにします。SET NULL は、子の行の外部キーをNULLにします。意図しない大量の削除を招くことがあるので、指定は慎重に行います。

Q: 関係データベースの主キーに関する記述として、適切なものはどれか。
ア: 主キーは、ほかの表の主キーを参照する列に設定する。
イ: 主キーは、一つの表に複数設定できる。
ウ: 主キーは、必ず一つの列だけで構成する。
エ: 主キーの値は、行を一意に識別でき、NULLにすることはできない。
正解: エ
解説: 主キーには、**一意であること**と、**NULLでないこと**が求められます。一つの表に設定できる主キーは一つですが、複数の列を組み合わせた複合キーにすることはできます。ほかの表の主キーを参照する列は、外部キーです。

Q: データウェアハウスで用いられるスタースキーマの説明として、適切なものはどれか。
ア: すべての表を、第3正規形まで正規化して、更新時の異状を防ぐ。
イ: 売上などの数値を持つファクト表を中心に、分析の切り口を表す複数のディメンション表を結び付ける。
ウ: 一つの表に、キーと値の組だけを格納する。
エ: 節と辺を用いて、データ同士のつながりを表現する。
正解: イ
解説: **スタースキーマ**は、中心のファクト表と、その周りの商品、店舗、日付などのディメンション表からなります。分析の問合せが単純になり、集計が速くなります。更新よりも参照を重視するので、あえて正規化を抑えます。
