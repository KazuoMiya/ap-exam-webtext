---本文
C社は、複数の会場で行われる公演のチケットを、会員向けのWebサイトで販売している。C社は、チケット予約システム（以下、本システムという）のデータベースを設計している。

### 〔業務の概要〕

- 会員は、会員番号で一意に識別される。
- 会場は複数あり、会場ごとに座席が決まっている。座席は、会場の中では座席番号で一意に識別されるが、異なる会場には同じ座席番号が存在する。座席には、S席、A席などの席種が決まっている。
- 公演は公演番号で一意に識別され、一つの会場で行われる。一つの会場では、日を変えて複数の公演が行われる。
- 料金は、公演と席種の組合せごとに決まる。
- 会員は、1回の予約で、一つの公演の座席を複数まとめて予約できる。予約は予約番号で一意に識別される。予約には状態があり、「確定」または「取消」のいずれかである。
- 予約した座席の1席ごとに、予約明細を記録する。予約明細には、予約した時点の料金を記録する。
- 同じ公演の同じ座席が、状態が「確定」の複数の予約に含まれてはならない。

設計した関係スキーマを図1に示す。下線は主キーを表す。外部キーは、ここでは表記を省略している。

### 〔会員別の購入金額の集計〕

状態が「確定」の予約について、会員ごとの料金の合計を求め、合計が10,000円以上の会員を、合計の大きい順に表示するSQL文を作成した。

```sql
SELECT 会員.会員番号, 会員.氏名, SUM(予約明細.料金) AS 合計
FROM 会員
  INNER JOIN 予約 ON 会員.会員番号 = 予約.会員番号
  INNER JOIN 予約明細 ON 予約.予約番号 = 予約明細.予約番号
WHERE   d
GROUP BY 会員.会員番号, 会員.氏名
  e   SUM(予約明細.料金) >= 10000
ORDER BY 合計   f
```

テスト用のデータは、表1、表2のとおりである。会員は、M1（青木）、M2（井上）、M3（上田）、M4（江藤）の4人が登録されている。

|---|---|---|---|
| 1 | M1 | K1 | 確定 |
| 2 | M1 | K2 | 確定 |
| 3 | M2 | K1 | 取消 |
| 4 | M3 | K1 | 確定 |
| 5 | M2 | K2 | 確定 |

### 〔会員別の予約件数の一覧〕

次に、すべての会員について、状態が「確定」の予約の件数を表示する一覧を作成することにした。予約のない会員も、件数を0として表示する。担当者は、次のSQL文を作成した。

```sql
SELECT 会員.会員番号, 会員.氏名, COUNT(予約.予約番号) AS 件数
FROM 会員
  LEFT OUTER JOIN 予約 ON 会員.会員番号 = 予約.会員番号
WHERE 予約.状態 = '確定'
GROUP BY 会員.会員番号, 会員.氏名
```

テストしたところ、①一部の会員が一覧に表示されなかった。担当者は、SQL文を修正した。

### 〔二重予約の防止〕

テストで、二人の会員がほぼ同時に同じ公演の同じ座席を予約したところ、両方の予約が確定してしまった。そこで、予約明細に、②同じ公演の同じ座席の行を重複して登録できないようにする制約を追加した。あわせて、③予約を取り消すときの予約明細の扱いを見直した。
---設問 1
図1の空欄 a〜c に入れる適切な属性名を答えよ。
---解答 1
- a：**会場番号**
- b：**会場番号**
- c：**席種**

解説：座席は「会場の中では座席番号で一意だが、異なる会場には同じ座席番号が存在する」ので、主キーは {会場番号, 座席番号} です。公演は「一つの会場で行われる」ので、会場番号を外部キーとして持ちます（一つの会場に複数の公演があるので、多の側の公演が外部キーを持つ）。料金は「公演と席種の組合せごと」なので、主キーは {公演番号, 席種} です。
---設問 2
〔会員別の購入金額の集計〕について、次の問いに答えよ。

（1）SQL文の空欄 d〜f に入れる適切な字句を答えよ。

（2）表1、表2のデータで、このSQL文を実行したときに表示される会員の氏名と合計を、表示される順にすべて答えよ。
---解答 2
（1）d：**予約.状態 = '確定'**　e：**HAVING**　f：**DESC**

（2）**青木 40,000**、**井上 12,000**

解説：確定の予約だけを対象にすると、青木は予約1（16,000円）と予約2（24,000円）で40,000円、井上は予約3が取消なので予約5の12,000円だけ、上田は予約4の8,000円です。上田は10,000円未満なので HAVING で除かれ、江藤は予約がないので内部結合の結果に現れません。行の条件は WHERE、集約した結果の条件は HAVING に書きます。
---設問 3
〔会員別の予約件数の一覧〕について、次の問いに答えよ。

（1）下線①について、表1のデータで表示されなかった会員の氏名を答えよ。また、表示されなかった理由を45字以内で述べよ。

（2）すべての会員が表示されるようにするには、SQL文をどのように修正すればよいか。35字以内で述べよ。
---解答 3
（1）氏名：**江藤**

理由の解答例：**外部結合で補われた行は状態がNULLで、WHERE句の条件を満たさず除かれるから。**

（2）解答例：**状態の条件をWHERE句から外し、ON句の結合条件に加える。**

解説：予約のない江藤は、左外部結合で予約側の列がNULLの行として残ります。しかし、その後の WHERE で「状態 ＝ '確定'」を判定すると、NULLとの比較は真にならないので除かれてしまい、内部結合と同じ結果になります。条件を ON 句に移す（`ON 会員.会員番号 = 予約.会員番号 AND 予約.状態 = '確定'`）と、結合する相手を確定の予約に限定したうえで、会員の全行が残ります。修正後は、青木2件、井上1件、上田1件、江藤0件になります。**外部結合と WHERE の組合せ**は、実務でも試験でも頻出の落とし穴です。
---設問 4
〔二重予約の防止〕について、次の問いに答えよ。

（1）下線②の制約の種類と、対象とする列の組合せを答えよ。

（2）下線③について、（1）の制約を追加した後、取り消された予約の予約明細の行を残したままにすると、どのような問題が起こるか。40字以内で述べよ。

（3）（1）の制約を追加した後、二人の会員が同時に同じ座席を予約したとき、後から登録しようとした処理はどうなるか。また、アプリケーションはその処理をどう扱うべきか。あわせて45字以内で述べよ。
---解答 4
（1）**一意性制約（UNIQUE制約）**を、**{公演番号, 座席番号}** に設定する。

（2）解答例：**取り消された座席の行が残り、ほかの会員がその座席を予約できなくなる。**

（3）解答例：**制約違反のエラーになるので、トランザクションをロールバックし、別の座席の選択を促す。**

採点のポイント：（1）は、予約明細に公演番号を持たせてあることが伏線です。予約番号から公演番号は分かりますが、予約明細の中だけで一意性を定義するために、あえて重複して持たせています。（2）は、表2で予約3（取消）と予約4（確定）が同じ座席A3を持っていることからも読み取れます。取消のときに予約明細の行を削除する（履歴が必要なら別の表に移す）必要があります。（3）は、制約によってDBMSが整合性を保証し、アプリケーションは失敗した側を正しく後始末する、という役割分担です。
