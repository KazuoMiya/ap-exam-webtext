## 補講：品質特性、設計の技法、開発管理

### ソフトウェアの品質特性（JIS X 25010）

製品品質モデルは、次の8つの特性で品質を整理します。

| 品質特性 | 内容 | 副特性の例 |
|---|---|---|
| 機能適合性 | 必要な機能を、正しく過不足なく提供する | 機能完全性、機能正確性 |
| 性能効率性 | 資源の量に対する性能 | 時間効率性、資源効率性 |
| 互換性 | 他の製品と情報を交換し、共存できる | 相互運用性 |
| 使用性 | 利用者が、有効に効率よく満足して使える | 習得性、運用操作性、アクセシビリティ |
| 信頼性 | 決められた条件で、機能を実行し続ける | 成熟性、可用性、障害許容性（耐故障性）、回復性 |
| セキュリティ | 情報やデータを保護する | 機密性、インテグリティ、否認防止性 |
| 保守性 | 修正や改良のしやすさ | モジュール性、解析性、修正性、試験性 |
| 移植性 | 別の環境へ移すことのしやすさ | 適応性、設置性、置換性 |

国際規格の2023年版では、安全性が加わるなどの再編が行われています。試験では、説明文がどの特性に当たるかを判断できれば十分です。

### 構造化設計とオブジェクト指向設計

- **DFD**でデータの流れを整理し、プログラムをモジュールに分割する。入力（源泉）、変換、出力（吸収）に分ける**STS分割**、処理の種類ごとに分ける**TR分割**（トランザクション分割）、共通の機能をまとめる共通機能分割がある
- クラス図の関係：**汎化**（is-a の関係。白抜きの三角形の矢印）、**集約**（part-of の関係。白抜きのひし形）、**コンポジション**（全体と部分の結び付きが強い集約。黒いひし形）、関連、依存
- **多重度**：関連する相手のインスタンスの数。「1」「0..1」「0..*」「1..*」のように書く

### デザインパターン

よく現れる設計上の問題への、定石となる解決策です。GoFの23パターンが有名です。

| パターン | 内容 |
|---|---|
| Singleton | あるクラスのインスタンスが、一つしか存在しないことを保証する |
| Factory Method | インスタンスの生成を、サブクラスに任せる |
| Adapter | インタフェースが合わないクラスを、変換して使えるようにする |
| Observer | あるオブジェクトの状態の変化を、依存するオブジェクトに通知する |
| Strategy | アルゴリズムを、実行時に切り替えられるようにする |
| Facade | 複雑な内部の処理に対する、単純な窓口を提供する |

**MVC**は、モデル（データと業務の処理）、ビュー（表示）、コントローラ（操作の受付と制御）に役割を分けるアーキテクチャのパターンです。

### テストの補足

- **エラー埋込法**（バグ埋込法）：意図的にバグを埋め込み、テストで見つかった割合から、元からあるバグの総数を推定する。埋め込んだバグ S 個のうち s 個が見つかり、元からのバグが n 個見つかったとき、元からのバグの総数の推定値は n × S ÷ s
- **状態遷移テスト**：状態遷移図や状態遷移表に基づき、遷移と、起きてはならない遷移を確認する
- **性能テスト**、**負荷テスト**（想定した負荷での動作）、**ストレステスト**（限界を超える負荷での動作）、**セキュリティテスト**
- **テストカバレッジ**（網羅率）：テストで実行した命令や分岐の割合。100％でも、仕様の漏れは見つけられない
- 自動化されたテストでは、依存する部品の代わりに**モック**や**スタブ**を使う

### 開発プロセスの成熟度と管理

- **CMMI**：組織の開発プロセスの成熟度を、5段階（初期、管理された、定義された、定量的に管理された、最適化している）で評価するモデル
- **ペアプログラミング**、**モブプログラミング**（チーム全員で1台の画面を見ながら開発する）
- **ベロシティ**：1回のスプリントでチームが完了できる作業量。計画の見積りに使う
- **バーンダウンチャート**：残りの作業量を時間の経過とともに示す。右下がりの線で、進捗を把握する
- **技術的負債**：その場しのぎの実装が積み重なり、後の変更を難しくするもの。リファクタリングで返済する
- **DevSecOps**：開発と運用の流れに、セキュリティの確認を最初から組み込む
- **ローコード開発**：画面上の設定や部品の組合せを中心に、少ないコードでアプリケーションを作る

### ソフトウェアの再利用と移行

- **リバースエンジニアリング**：既存のプログラムから、仕様や設計を導き出す。**フォワードエンジニアリング**：仕様から新しいシステムを作る。両者を組み合わせて作り直すのが**リエンジニアリング**
- **マイグレーション**：既存のシステムを、新しい環境へ移行する。業務の機能を変えずに基盤だけを移す方法をリホスト、言語を変換する方法をリライトという
- 移行の方式には、一度に切り替える**一斉移行**、機能や拠点ごとに順に切り替える**段階移行**、新旧を同時に動かして結果を比べる**並行運用**がある
