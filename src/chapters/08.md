## データベースの基本

### 3層スキーマ

| スキーマ | 内容 |
|---|---|
| 外部スキーマ | 利用者やアプリケーションから見たデータの見え方（ビュー） |
| 概念スキーマ | データベース全体の論理的な構造（表の定義） |
| 内部スキーマ | 記憶装置上の物理的な格納方法（索引、ファイル編成） |

スキーマを分けることで、物理的な格納方法を変えてもアプリケーションに影響しない**データの独立性**が得られます。

### 関係モデルとキー

関係データベースは、データを行（タプル）と列（属性）からなる表（関係）で表します。

| 用語 | 意味 |
|---|---|
| 候補キー | 行を一意に識別できる、必要最小限の属性の組 |
| 主キー | 候補キーから選んだ1つ。NULL不可、重複不可 |
| 外部キー | 他の表の主キーを参照する属性。**参照制約**により、参照先に存在しない値は登録できない |
| スーパキー | 行を一意に識別できる属性の組（余分な属性を含んでもよい） |

### E-R図

実体（エンティティ）と関連（リレーションシップ）で、データの構造を表します。関連には 1対1、1対多、多対多 があります。**多対多の関連は、そのままでは表にできない**ため、両方の主キーを持つ連関エンティティ（例：学生と科目の間の「履修」）を作り、2つの1対多に分解します。

## 正規化

データの重複をなくし、更新時の矛盾（更新時異状）を防ぐために表を分割することを**正規化**といいます。

<div class="box point" markdown="1">

**関数従属**：属性 X の値が決まると属性 Y の値が1つに決まるとき、「Y は X に関数従属する」（X → Y）と表します。

</div>

| 正規形 | 条件 |
|---|---|
| 第1正規形 | 繰返し項目がなく、すべての属性が単一の値をもつ |
| 第2正規形 | 第1正規形で、主キーの一部だけに従属する属性（**部分関数従属**）がない |
| 第3正規形 | 第2正規形で、主キー以外の属性を経由して従属する属性（**推移的関数従属**）がない |
| ボイス・コッド正規形 | 自明でないすべての関数従属の決定項が、候補キーを含む属性の組（スーパキー）である |

<div class="box example" markdown="1">

受注明細（**受注番号**, **商品番号**, 商品名, 数量）で、主キーは {受注番号, 商品番号}。商品名は商品番号だけで決まるので部分関数従属があり、第1正規形にとどまります。商品（**商品番号**, 商品名）を分けると第2正規形になります。

社員（**社員番号**, 氏名, 部署コード, 部署名）では、部署名が 社員番号 → 部署コード → 部署名 と推移的に従属するので第2正規形です。部署（**部署コード**, 部署名）を分けると第3正規形になります。

</div>

正規化を進めすぎると結合が増えて性能が落ちるため、参照性能を優先してあえて正規化を崩す**非正規化**を行うこともあります。

## SQL

### SELECT文の基本形

```sql
SELECT 列名, 集約関数(列名)
FROM 表名
WHERE 行の条件
GROUP BY グループ化する列
HAVING グループの条件
ORDER BY 並べ替える列 [ASC | DESC]
```

処理は **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY** の順に行われると考えると、結果を求めやすくなります。

- **WHERE** はグループ化の前に行を絞る。**HAVING** はグループ化の後にグループを絞る。集約関数の条件は HAVING に書く
- 集約関数：COUNT、SUM、AVG、MAX、MIN。COUNT(*) は行数、COUNT(列) はNULLを除いた件数
- DISTINCT は重複行を除く

### 結合

| 結合 | 結果 |
|---|---|
| 内部結合（INNER JOIN） | 両方の表で結合条件に一致する行だけ |
| 左外部結合（LEFT OUTER JOIN） | 左の表の全行。一致する行がなければ右の表の列はNULL |
| 完全外部結合（FULL OUTER JOIN） | 両方の表の全行 |

### 副問合せ

```sql
-- 注文したことのない顧客
SELECT 顧客名 FROM 顧客
WHERE NOT EXISTS (
  SELECT * FROM 注文 WHERE 注文.顧客番号 = 顧客.顧客番号
)
```

外側の行ごとに内側を評価する副問合せを**相関副問合せ**といいます。

<div class="box caution" markdown="1">

副問合せの結果にNULLが含まれると、`NOT IN` は比較結果が「不明」になり、1行も返さなくなります。NULLを含む可能性がある列では `NOT EXISTS` を使うのが安全です。

</div>

### その他の文

- データ操作：INSERT、UPDATE、DELETE
- データ定義：CREATE TABLE（PRIMARY KEY、FOREIGN KEY、NOT NULL、UNIQUE、CHECK などの制約）、CREATE VIEW
- 権限：GRANT、REVOKE

### 関係代数

| 演算 | 内容 |
|---|---|
| 選択 | 条件に合う**行**を取り出す（SQLのWHERE） |
| 射影 | 指定した**列**を取り出す（SQLのSELECT句の列指定） |
| 結合 | 共通の属性で2つの表を組み合わせる |
| 和・差・共通 | 同じ構造の表どうしの集合演算（UNION、EXCEPT、INTERSECT） |
| 直積 | 2つの表の行のすべての組合せ |

## トランザクション処理

### ACID特性

| 特性 | 内容 |
|---|---|
| 原子性（Atomicity） | すべて実行されるか、まったく実行されないかのどちらか |
| 一貫性（Consistency） | トランザクションの前後でデータの整合性が保たれる |
| 独立性（Isolation） | 同時に実行しても、互いに影響を与えない |
| 耐久性（Durability） | コミットした結果は障害が起きても失われない |

### 排他制御

| ロック | 他のトランザクションの読取り | 他のトランザクションの更新 |
|---|---|---|
| 共有ロック（読取り用） | 可（共有ロックどうしは両立） | 不可 |
| 専有ロック（更新用） | 不可 | 不可 |

**2相ロック方式**は、必要なロックをすべて獲得し終えてから解放を始める方式で、直列化可能性（順番に実行したのと同じ結果）を保証します。ロックの単位（粒度）を大きくすると管理は楽になりますが、同時実行性は下がります。

ロックを使わず、更新時に他から変更されていないかを確認する**楽観的排他制御**もあります。競合が少ない場合に効率的です。

排他制御を行わないと、次の図のように、一方の更新が失われることがあります。二つのトランザクションが、同じ値を読み取り、それぞれの計算の結果で上書きするからです。

### 隔離性水準

| 水準 | ダーティリード | ノンリピータブルリード | ファントムリード |
|---|---|---|---|
| READ UNCOMMITTED | 起こる | 起こる | 起こる |
| READ COMMITTED | 起こらない | 起こる | 起こる |
| REPEATABLE READ | 起こらない | 起こらない | 起こる |
| SERIALIZABLE | 起こらない | 起こらない | 起こらない |

- ダーティリード：他のトランザクションの**未コミット**の更新を読んでしまう
- ノンリピータブルリード：同じ行を2回読むと、間に他がコミットした更新で値が変わっている
- ファントムリード：同じ条件で2回検索すると、間に他が追加した行が現れる

### 障害回復

| ログ | 用途 |
|---|---|
| 更新前ログ（ジャーナル） | 更新を取り消す**ロールバック**に使う |
| 更新後ログ | 更新をやり直す**ロールフォワード**に使う |

**チェックポイント**では、メモリ上の更新内容をデータベースに書き出します。システム障害が起きたときは次のように回復します。

- チェックポイント後、障害発生までに**コミット済み**のトランザクション → 更新後ログでロールフォワード
- 障害発生時点で**未コミット**のトランザクション → 更新前ログでロールバック
- チェックポイント前にコミット済みのトランザクション → 処理不要

媒体障害（ディスクの故障）のときは、バックアップから復元した後、更新後ログでロールフォワードします。ログをデータベースより先に書き出す**WAL**（ログ先行書込み）が基本です。

## データベースの応用

### 分散データベース

複数のサイトに分散したデータを1つのデータベースのように扱います。**2相コミット**では、調整役がすべての参加サイトに「コミットできるか」を問い合わせ（第1相）、全員が可と答えたらコミットを指示します（第2相）。1つでも不可ならロールバックを指示します。

**レプリケーション**はデータの複製を別のサイトに持ち、障害対策や参照負荷の分散に使います。

### NoSQL

| 種類 | 特徴 |
|---|---|
| キーバリュー型 | キーと値の組で格納。単純で高速、水平分散しやすい |
| ドキュメント型 | JSONなどの構造をもつ文書単位で格納 |
| 列指向型 | 列単位で格納。大量データの集計に強い |
| グラフ型 | ノードとエッジで関係を表す。SNSの関係の分析など |

分散システムでは、一貫性（Consistency）、可用性（Availability）、分断耐性（Partition tolerance）を同時にすべては満たせないという**CAP定理**が知られています。NoSQLの多くは、一時的な不整合を許して最終的に一貫させる（結果整合性）**BASE**特性を重視します。

### データ分析の基盤

- **データウェアハウス**：業務システムから集めたデータを、分析しやすい形で時系列に蓄積する
- **データマート**：目的や部門ごとにデータウェアハウスから切り出したもの
- **データレイク**：構造化・非構造化を問わず、生データをそのまま蓄える
- **OLAP**：多次元のデータを、ドリルダウン（詳細へ）、ロールアップ（集約へ）、スライス（切り口を固定）などで対話的に分析する
- **データマイニング**：大量のデータから、相関やパターンなど有用な規則を発見する
- **索引**：B＋木索引は範囲検索に強く、ハッシュ索引は一致検索に強い
