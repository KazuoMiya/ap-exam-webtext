## 開発プロセスと手法

### 主な開発モデル

| モデル | 特徴 |
|---|---|
| ウォーターフォール | 要件定義 → 設計 → 実装 → テストと工程を順に進め、原則として前の工程に戻らない。計画や進捗を管理しやすい |
| プロトタイピング | 早い段階で試作品を作り、利用者の評価を得ながら要件を固める |
| スパイラル | 設計・実装・評価を繰り返し、リスクを分析しながら段階的に完成度を上げる |
| アジャイル | 短い期間の反復で、動くソフトウェアを継続的に提供し、変化に柔軟に対応する |

**共通フレーム2013**（SLCP-JCF2013）は、ソフトウェアの企画から開発、運用、保守、廃棄までの作業内容と用語を標準化した枠組みで、発注者と受注者が共通の言葉で作業範囲を合意するために使います。

### スクラム

| 要素 | 内容 |
|---|---|
| プロダクトオーナー | プロダクトの価値を最大化する責任者。プロダクトバックログの優先順位を決める |
| スクラムマスター | スクラムが正しく実践されるよう支援し、障害を取り除く |
| 開発者 | 各スプリントで、使える成果物（インクリメント）を作る |
| スプリント | 1か月以内の固定された期間の反復 |
| プロダクトバックログ | プロダクトに必要な項目を優先順位順に並べた一覧 |
| デイリースクラム | 毎日15分程度で進捗と計画を確認する |
| スプリントレビュー | 成果物をステークホルダに示し、フィードバックを得る |
| スプリントレトロスペクティブ | 進め方を振り返り、改善策を決める |

### XP（エクストリームプログラミング）

- **テスト駆動開発（TDD）**：先にテストを書き、テストに通る最小限のコードを書き、リファクタリングする
- **ペアプログラミング**：2人1組で、1人がコードを書き、もう1人がレビューしながら進める
- **リファクタリング**：外部から見た振る舞いを変えずに、内部の構造を改善する
- **継続的インテグレーション（CI）**：変更を頻繁に統合し、自動でビルドとテストを行う

**DevOps** は開発と運用が協力して、価値を素早く安定して届ける取組みです。テスト済みの変更をいつでもリリースできる状態に保つ **CD**（継続的デリバリー）と組み合わせます。

## 要件定義と設計

### 要件の種類

- **機能要件**：システムが何をするか（受注の登録、在庫の照会など）
- **非機能要件**：性能（応答時間）、可用性（稼働率）、セキュリティ、保守性、移行性など、機能以外の品質に関する要件

### UMLの主な図

| 図 | 表すもの |
|---|---|
| ユースケース図 | 利用者（アクター）とシステムの機能（ユースケース）の関係 |
| クラス図 | クラスの属性、操作、クラス間の関係（関連、汎化、集約） |
| シーケンス図 | オブジェクト間のメッセージのやり取りを**時系列**で表す |
| コミュニケーション図 | オブジェクト間のメッセージのやり取りを**つながり**に着目して表す |
| アクティビティ図 | 処理の流れ。業務フローや並行処理も表せる |
| ステートマシン図 | オブジェクトの状態と、イベントによる状態の遷移 |

構造化分析では、データの流れを **DFD**（データフロー図）で表します。DFDの要素は、プロセス、データフロー、データストア、外部実体（源泉・吸収）の4つです。

### モジュールの独立性

モジュールは**強度（凝集度）を高く**、**結合度を低く**するほど独立性が高く、保守しやすくなります。

| 強度（凝集度） | 高い順 |
|---|---|
| 機能的強度 | 1つの機能だけを実行する（最も望ましい） |
| 情報的強度 | 同じデータを扱う複数の機能を、入口を分けてまとめる |
| 連絡的強度 | 同じデータを使う処理を順に実行する |
| 手順的強度 | 関連する処理を決められた順に実行する |
| 時間的強度 | 初期化処理のように、同じ時期に実行する処理をまとめる |
| 論理的強度 | 関連する複数の機能を引数で切り替える |
| 暗合的強度 | 関係のない処理をまとめる（最も望ましくない） |

| 結合度 | 弱い（望ましい）順 |
|---|---|
| データ結合 | 必要なデータ項目だけを引数で渡す（最も望ましい） |
| スタンプ結合 | 構造体などのデータ構造を引数で渡し、その一部だけを使う |
| 制御結合 | 処理を切り替えるための制御情報を引数で渡す |
| 外部結合 | 単一のデータを外部宣言して共有する |
| 共通結合 | 複数のデータを共通領域に置いて共有する |
| 内容結合 | 他のモジュールの内部を直接参照する（最も望ましくない） |

## テスト

### テストの工程

単体テスト（モジュール単位）→ 結合テスト（モジュール間のインタフェース）→ システムテスト（要件を満たすか）→ 運用テスト・受入れテスト（利用者の環境で業務に使えるか）の順に行います。プログラムを修正した後は、修正していない部分に悪影響がないかを確かめる**回帰テスト**（リグレッションテスト）を行います。

### 結合テストの進め方

| 方式 | 進め方 | 必要な仮のモジュール |
|---|---|---|
| トップダウンテスト | 上位のモジュールから順に結合する | 下位の代わりの**スタブ** |
| ボトムアップテスト | 下位のモジュールから順に結合する | 上位の代わりの**ドライバ** |
| ビッグバンテスト | すべてを一度に結合する | なし。不具合の箇所を特定しにくい |

### ブラックボックステスト

内部の構造を考えず、仕様に基づいて入力と出力を確かめます。

- **同値分割**：入力を、同じ扱いになるグループ（有効同値クラス、無効同値クラス）に分け、各グループから代表値を選ぶ
- **限界値分析**：グループの境界の値と、その前後の値を選ぶ。入力範囲が1〜100なら 0、1、100、101
- **デシジョンテーブル**、**原因結果グラフ**：入力条件の組合せと、その結果を整理してテストケースを作る

### ホワイトボックステスト

プログラムの内部の構造（制御の流れ）に基づいて、どこまで実行したか（網羅率）を基準にします。

| 網羅基準 | 条件 |
|---|---|
| 命令網羅 | すべての命令を少なくとも1回実行する |
| 判定条件網羅（分岐網羅） | 各判定の真と偽を少なくとも1回ずつ実行する |
| 条件網羅 | 判定を構成する個々の条件の真と偽を少なくとも1回ずつ実行する |
| 判定条件／条件網羅 | 判定条件網羅と条件網羅をともに満たす |
| 複数条件網羅 | 個々の条件の真偽の**すべての組合せ**を実行する。条件が n 個なら 2<sup>n</sup> 通り |

<div class="box caution" markdown="1">

条件網羅を満たしても、判定条件網羅を満たすとは限りません。「A AND B」で (A, B) ＝ (真, 偽) と (偽, 真) を試すと、各条件の真偽はそろいますが、判定はどちらも偽になり、真の分岐が実行されません。

</div>

### 品質の管理

テストで見つかったバグの累積数は、時間とともに増え方が緩やかになり、一定の値に近づく**ゴンペルツ曲線**（信頼度成長曲線）を描くのが理想です。曲線が飽和していれば、品質が安定してきたと判断できます。

## レビュー

| 手法 | 内容 |
|---|---|
| ウォークスルー | 作成者が主体となり、成果物を説明しながら参加者が誤りを指摘する |
| インスペクション | **モデレータ**が進行役となり、役割分担と手順を決めて公式に行う。結果を記録し、修正を確認する |
| ラウンドロビン | 参加者が持ち回りで責任者を務め、レビューを進める |
| ピアレビュー | 同じ立場の開発者どうしで行う |

レビューでは誤りの指摘に集中し、作成者個人の評価や、解決策の議論に時間を使いすぎないようにします。

## 保守と構成管理

### 保守の分類（JIS X 0161）

| 種類 | 内容 |
|---|---|
| 是正保守 | 発見された不具合を修正する |
| 予防保守 | 潜在的な不具合が問題になる前に修正する |
| 適応保守 | OSの更新や法改正など、環境の変化に合わせて変更する |
| 完全化保守 | 性能や保守性を改善する |

### 構成管理と開発環境

**構成管理**は、ソースコードやドキュメントなどの構成要素とその版を識別し、変更を管理して整合性を保つ活動です。Git などのバージョン管理システムでは、ブランチで並行して開発し、レビュー後にマージします。

既存のプログラムを解析して仕様や設計を明らかにすることを**リバースエンジニアリング**、複数のWebサービスのAPIを組み合わせて新しいサービスを作ることを**マッシュアップ**といいます。
