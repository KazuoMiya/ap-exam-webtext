## 補講1：暗号と認証の仕組みを深く理解する

### 共通鍵暗号の利用モード

ブロック暗号（AESは128ビット単位）で長いデータを暗号化するときの手順を**暗号利用モード**といいます。

| モード | 特徴 |
|---|---|
| ECB | ブロックごとに独立して暗号化する。同じ平文ブロックは同じ暗号文になり、パターンが漏れるので使わない |
| CBC | 直前の暗号文ブロックと平文をXORしてから暗号化する。最初のブロックには初期化ベクトル（IV）を使う |
| CTR | カウンタ値を暗号化した結果と平文をXORする。並列処理ができる |
| GCM | CTRモードに認証（改ざん検知）を加えた**認証付き暗号**。TLS 1.3 で標準的に使われる |

### 鍵共有と前方秘匿性

**ディフィー・ヘルマン（DH）鍵共有**は、盗聴されている通信路でも、双方が公開する値から同じ共通鍵を計算できる方式です。ただし相手の認証はしないので、単独では中間者攻撃を防げません。ディジタル署名や証明書と組み合わせて使います。

通信のたびに使い捨ての鍵ペアで鍵共有を行う（DHE、ECDHE）と、将来サーバの秘密鍵が漏れても、過去に記録された暗号通信は復号できません。この性質を**前方秘匿性（PFS）**といいます。

### 暗号の強度と危殆化

- 計算機の性能向上や解読法の進歩で、暗号の安全性が低下することを**危殆化**という
- **CRYPTREC**は、電子政府で利用を推奨する暗号のリスト（CRYPTREC暗号リスト）を公表している
- 同程度の安全性を得るのに、楕円曲線暗号はRSAよりずっと短い鍵で済む（RSA 2048ビット ≒ 楕円曲線 224ビット程度）
- 量子コンピュータが実用化されるとRSAや楕円曲線暗号は解読されるおそれがあり、**耐量子計算機暗号（PQC）**への移行が進められている
- ハッシュ関数は、MD5とSHA-1は衝突が見つかっており使わない。SHA-2（SHA-256など）、SHA-3を使う

### TLSの流れ

TLSは、**サーバの認証**、**鍵交換**、**暗号化と改ざん検知**を提供します。TLS 1.3 のハンドシェイクの概要は次のとおりです。

1. クライアントが、対応する暗号スイートと鍵共有用の公開値を送る（ClientHello）
2. サーバが、選んだ暗号スイート、鍵共有用の公開値、**サーバ証明書**、ハンドシェイクへの署名を返す（ServerHello ほか）
3. クライアントは証明書を検証する。確認するのは、信頼する認証局から証明書チェーンをたどれること、有効期限内であること、失効していないこと、**証明書のドメイン名が接続先と一致すること**
4. 双方が鍵共有の結果から共通鍵を導出し、以降は共通鍵暗号（認証付き暗号）で通信する

TLS 1.3 は、鍵交換を前方秘匿性のある方式に限定し、安全でない暗号方式を廃止し、往復回数を減らして高速化しています。クライアントも証明書を提示する方式を**クライアント認証**（相互TLS）といいます。

証明書の種類には、ドメインの管理権限だけを確認するDV、組織の実在も確認するOV、より厳格に審査するEVがあります。どれも暗号化の強度は同じで、違うのは認証局による審査の厳しさです。

### ネットワークの認証基盤

| 技術 | 内容 |
|---|---|
| IEEE 802.1X | LANに接続する機器や利用者を認証する規格。**サプリカント**（端末）、**オーセンティケータ**（スイッチや無線LANアクセスポイント）、**認証サーバ**（RADIUSサーバ）で構成する |
| RADIUS | 認証（Authentication）、認可（Authorization）、アカウンティング（Accounting）を一元管理するプロトコル |
| EAP | 802.1Xで使う認証の枠組み。EAP-TLS はサーバとクライアントの双方が証明書で認証する。PEAP はサーバ証明書で保護した通信路の中でIDとパスワードによる認証を行う |
| Kerberos | 認証サーバが発行する**チケット**でシングルサインオンを実現する。パスワードをネットワークに流さない。時刻の同期が前提 |
| LDAP | ディレクトリサービス（利用者や機器の情報の一元管理）にアクセスするプロトコル |

無線LANでは、WPA2/WPA3 の**エンタープライズ**モードが802.1X認証を使い、**パーソナル**モードは事前共有鍵（PSK）を使います。WPA3 はパスワードから鍵を導く方式をSAEに改め、辞書攻撃に強くなっています。

### アクセス制御の考え方

- **最小権限の原則**：業務に必要な最小限の権限だけを与える
- **Need-to-know**：知る必要のある人にだけ情報へのアクセスを認める
- **職務分掌**：1人で不正を完結できないよう、権限を分ける
- 任意アクセス制御（DAC）は資源の所有者が権限を決め、強制アクセス制御（MAC）は管理者が定めた規則をシステムが強制する。ロールベースアクセス制御（RBAC）は役割に権限を割り当てる
- **特権ID**は、利用の申請と承認、利用者の特定、操作ログの記録と第三者による確認を組み合わせて管理する

## 補講2：Webとメールのセキュリティを実装レベルで押さえる

### Cookieの属性とHTTPヘッダ

| 設定 | 効果 |
|---|---|
| Secure属性 | HTTPS通信のときだけCookieを送る。盗聴による漏えいを防ぐ |
| HttpOnly属性 | JavaScriptからCookieを読めなくする。XSSによるセッションIDの窃取を緩和する |
| SameSite属性 | 他サイトから発生したリクエストにCookieを付けるかを制御する。CSRFを緩和する |
| HSTS | 以降の接続を必ずHTTPSで行うよう、Webサーバがブラウザに指示する |
| CSP（Content Security Policy） | スクリプトなどの読込み元を制限し、XSSの影響を抑える |
| X-Frame-Options、CSPのframe-ancestors | 他サイトのフレーム内への表示を禁止し、**クリックジャッキング**を防ぐ |

**同一オリジンポリシー**は、スキーム、ホスト、ポートの組（オリジン）が異なるサイトの情報に、スクリプトからアクセスすることを制限するブラウザの基本的な仕組みです。必要な場合だけ、サーバ側が**CORS**のヘッダで許可します。

### セッション管理の要点

- セッションIDは、推測できない十分な長さの乱数にする
- **ログインに成功したら新しいセッションIDを発行する**。攻撃者が用意したIDを使わせる**セッション固定攻撃**（セッションフィクセーション）を防ぐ
- セッションIDをURLに含めない。Refererヘッダやログから漏れるため
- ログアウト時と一定時間の無操作でセッションを無効にする

### 攻撃と対策の対応

| 攻撃 | 根本的な対策 | 保険的な対策 |
|---|---|---|
| SQLインジェクション | プレースホルダでSQL文を組み立てる | DBアカウントの権限を最小にする、エラーの詳細を表示しない、WAF |
| XSS | 出力するすべての値をエスケープする。URLは http と https だけを許可する | HttpOnly、CSP、WAF |
| CSRF | 秘密のトークンを埋め込み照合する。重要な操作の前に再認証する | SameSite属性、Refererの確認 |
| OSコマンドインジェクション | シェルを呼び出す機能を使わない | 入力値の検証 |
| ディレクトリトラバーサル | 外部からファイル名を直接指定させない | ディレクトリを固定し、パスを正規化して確認する |
| SSRF | サーバから接続できる宛先を許可リストで制限する | 内部ネットワークへのアクセス制御 |

**SSRF**（サーバサイドリクエストフォージェリ）は、サーバに任意のURLへリクエストを送らせ、外部から直接届かない内部のサーバやクラウドの管理用の情報にアクセスする攻撃です。

入力値の検証は**サーバ側で必ず行います**。ブラウザ側のJavaScriptによるチェックは利用者の利便のためのもので、攻撃者は簡単に回避できます。

### メールの暗号化となりすまし対策

- **STARTTLS**：SMTPなどの通信を途中からTLSで暗号化する。サーバ間の経路を保護するが、サーバ上では平文になる
- **S/MIME**、PGP：メール本文を端末間で暗号化し、署名する
- **SMTP-AUTH**：メール送信時に利用者を認証する。サブミッションポート（587番）と組み合わせる
- SPF、DKIM、DMARC：送信ドメインを認証する（本文の表を参照）。SPFはメールが転送されると失敗しやすく、DKIMは署名が付いているので転送に強い

## 補講3：防御の設計、運用、インシデント対応

### ファイアウォールのルールの読み方

パケットフィルタリング型のファイアウォールは、送信元、宛先、プロトコル、ポート番号の条件で通信を許可または拒否します。

- ルールは**上から順に**評価し、最初に一致したルールを適用する
- どのルールにも一致しない通信は拒否する（**デフォルト拒否**）のが原則
- **ステートフルインスペクション**は、通信の状態を記憶し、内側から始めた通信への応答だけを自動で通す。戻りの通信のためのルールを個別に書く必要がない
- 必要な通信だけを許可する**ホワイトリスト方式**が基本

| 番号 | 送信元 | 宛先 | ポート | 動作 |
|---|---|---|---|---|
| 1 | インターネット | DMZのWebサーバ | TCP 443 | 許可 |
| 2 | DMZのWebサーバ | 内部のDBサーバ | TCP 5432 | 許可 |
| 3 | 内部LAN | DMZのプロキシ | TCP 8080 | 許可 |
| 4 | すべて | すべて | すべて | 拒否 |

この例では、インターネットから内部のDBサーバへ直接届く経路はありません。Webサーバが侵害されても、内部へ届くのはDBのポートだけに限定されます。

### 多層防御と侵入後の対策

1つの対策が破られても次の対策で防ぐ考え方を**多層防御**といいます。侵入を完全には防げない前提で、次の3段階を組み合わせます。

- **入口対策**：ファイアウォール、メールフィルタ、マルウェア対策、脆弱性の修正
- **内部対策**：ネットワークの分割、権限の最小化、EDR、ログの監視。侵入後に他の機器へ感染を広げる**横展開**（ラテラルムーブメント）を防ぐ
- **出口対策**：プロキシでの通信先の制限と認証、C&Cサーバへの通信の検知と遮断

攻撃の段階を整理する枠組みに**サイバーキルチェーン**（偵察、武器化、配送、攻撃、インストール、遠隔操作、目的の実行）があり、どこか1つの段階で断ち切れば被害を防げると考えます。攻撃者の戦術と技術を体系化した知識ベースが**MITRE ATT&CK**です。

### ランサムウェアへの備え

- バックアップを**ネットワークから切り離して**（オフライン、書換え不能な媒体）保管する。ネットワーク上のバックアップは一緒に暗号化されるおそれがある
- **3-2-1ルール**：データを3つ持ち、2種類の媒体に保存し、1つは遠隔地に置く
- バックアップから実際に復元できることを定期的に試す
- VPN装置やリモートデスクトップの脆弱性の修正と、多要素認証の導入。侵入口として特に狙われる

### 脆弱性の管理

| 用語 | 内容 |
|---|---|
| CVE | 個々の脆弱性に付ける世界共通の識別番号 |
| CWE | 脆弱性の種類（SQLインジェクションなど）を分類する一覧 |
| CVSS | 脆弱性の深刻度を0.0〜10.0で評価する。基本評価基準、現状評価基準、環境評価基準からなる |
| SBOM | ソフトウェアを構成する部品（ライブラリなど）の一覧表。使っている部品に脆弱性が見つかったとき、影響範囲をすぐ特定できる |
| ファジング | 問題を起こしそうなデータを大量に送り込み、異常な動作から未知の脆弱性を見つける検査 |

深刻度だけでなく、インターネットから到達できるか、すでに攻撃に悪用されているかを考慮して、修正の優先順位を決めます。

### インシデント対応の流れ

**検知と連絡受付 → トリアージ（優先度の判断）→ 初動対応（封じ込め）→ 原因の調査 → 根絶と復旧 → 再発防止と報告** の順に進めます。

### ハードウェアに基づく保護

| 技術 | 内容 |
|---|---|
| 耐タンパ性 | 外部から内部の情報を読み出したり改ざんしたりすることへの耐性 |
| TPM | 鍵の生成と保管、機器の構成の計測を行うセキュリティチップ。ディスク暗号化の鍵の保護に使う |
| HSM | 暗号鍵を安全に生成、保管し、内部で暗号処理を行う専用装置。認証局や決済システムで使う |
| セキュアブート | 起動時にソフトウェアのディジタル署名を検証し、改ざんされたものを起動させない |
| サイドチャネル攻撃 | 処理時間、消費電力、電磁波などから秘密情報を推測する攻撃 |

### 組織、制度、ガイドライン

| 名称 | 役割 |
|---|---|
| 国家サイバー統括室（NCO） | 国のサイバーセキュリティ政策の司令塔。2025年7月に内閣サイバーセキュリティセンター（NISC）を改組して発足 |
| JPCERT/CC | 国内のインシデント対応の調整役。国際的な窓口も担う |

| J-CSIP | 重要インフラ企業などが、標的型攻撃の情報をIPAを介して共有する取組み |

| PCI DSS | クレジットカードの会員データを扱う事業者向けの国際的なセキュリティ基準 |
| プライバシーマーク | JIS Q 15001 に基づき、個人情報を適切に取り扱う事業者を認定する制度 |

### 人と組織の対策

内部不正は、**動機**、**機会**、**正当化**の3つがそろうと起こりやすい（不正のトライアングル）とされます。技術的な対策で機会を減らすだけでなく、処遇への不満などの動機や、「みんなやっている」といった正当化を生まない組織づくりが必要です。

標的型攻撃メールの訓練は、開封率を下げることよりも、開いてしまったときに**すぐ報告する**行動を定着させることが目的です。
